# Windows worker runtime

The .NET 8 worker is a Windows Service and self-contained single-file executable. It listens only on `127.0.0.1:8765`; the controller must create an authenticated SSM forwarding session and use mutual TLS. There is no plaintext fallback. Configure a server PEM certificate/key, controller CA and exact controller leaf thumbprint in a protected host-local `worker.json`. Missing enrollment material fails startup. Keep private keys out of user data, source, environment variables and command output. TLS validates certificate validity, client-auth usage, private CA chain and exact enrolled leaf pin. Offline private-CA validation does not perform network revocation checks; rotate the enrollment and exact pin to revoke a controller.

## Provision and enroll

`Bootstrap-Worker.ps1` implements the controller's two-phase remote provisioning route. `Request` accepts an immutable public worker release URL and SHA-256, installs verified official Git/GitHub CLI/Codex and Node 22 packages, creates the dedicated standard service account, grants service logon, initializes its stable profile, applies restricted enrollment/data ACLs, registers the service and generates a local RSA key plus public CSR. Only `{ workerId, csr }` is returned. Official release metadata pins each resolved tool version and SHA-256 before execution; unavailable hashes fail closed. `Complete` accepts only public signed server-certificate and CA material plus the controller leaf SHA-256 DER pin, writes protected configuration, starts the service and reports loopback-listener state. The controller must independently verify `/health` with mutual TLS before readiness. `Repair` and `Update` preserve the account, private key, configuration, repositories and worktrees; they reject an active account-owned app-server, stage/hash/backup before stopping, restore the prior executable if replacement fails, and return the preserved-key CSR. Initial `Request` refuses an existing installation rather than guessing ownership. These scripts are parsed but have not been executed on a cloud worker.

All four phases require the exact retained EBS `DataVolumeId`. Disk serials are normalized and matched to that exact ID; ambiguous, system or boot disks are rejected. Only `Request` initializes a matching RAW data disk. Existing NTFS partitions are reused without formatting, and `Repair`/`Update` reject RAW or ambiguous existing volumes. Workspaces and durable task metadata live in `FleetWorkspaces` on that volume, with the worker's modify ACL. A recorded volume ID/path mismatch stops provisioning. This source-level safety contract still needs a real remote-host receipt.

1. Supply a reviewed immutable prerequisite manifest to `worker/scripts/Install-Prerequisites.ps1`. Each of `git`, `gh`, `node`, `codex` and `dotnet` requires an explicit version, official HTTPS download URL, SHA-256 and `exe`, `msi` or `zip` kind. No unverified latest download or placeholder hash is accepted. Obtain hashes from an authenticated official release source independently of the download. ZIP packages are extracted once and require absolute executable configuration. Package discovery and automatic version reuse remain incomplete.
2. Build through the root build entrypoint. Packaging must publish `worker/Fleet.Worker.csproj` with `dotnet publish -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true`. A self-contained build needs no separately installed .NET runtime.
3. Use the reviewed `Install-Worker.ps1` on the intended worker host. It creates a stable dedicated standard account when absent, refuses administrator membership, and registers the Windows Service using a native protected credential object. It never enables automatic sign-in or changes security controls. Existing services are preserved. Service-logon rights, enrollment/data ACLs and the first service start are explicit host provisioning steps, not completed automatically by this revision.
4. The service and all CLI children run under that one stable profile. Authenticate through `/auth/codex/start` and `/auth/github/start`; no personal controller profile is copied. Device authentication and GitHub CLI use a real ConPTY. Send bounded keyboard input to `/auth/:provider/input`. Only the transient authentication endpoint exposes extracted one-time links and codes with `Cache-Control: no-store`. ANSI terminal output, credentials and raw CLI output are never written to service logs or general events. Expiry is null when the CLI does not provide authoritative expiry; the worker cancels its wait after fifteen minutes rather than claiming an invented provider expiry.
5. Successful login requires `codex login status` or `gh auth status --hostname github.com`. GitHub verification additionally requires `gh auth setup-git`. Pairing invokes `codex remote-control start --json` and `pair --json`; its parser uses the official CLI's `manualPairingCode` and Unix-seconds `expiresAt` fields, as defined in [the CLI source](https://github.com/openai/codex/blob/main/codex-rs/cli/src/remote_control_cmd.rs). Code issuance remains `code-issued`, never a verified remote connection. Pairing connection-state verification is not implemented.

## Dispatch, interact and recover

`POST /tasks` accepts `{ id?, repositoryUrl, prompt, model? }`. IDs are UUIDs and retries with the same ID return existing metadata. Only one task is active at a time. The controller owns its persistent FIFO. A worker clones an HTTPS repository into an ID-owned directory, creates a separate branch and Git worktree, launches `codex app-server --stdio`, initializes, creates a thread, then starts a turn with a workspace-write sandbox and on-request approvals. Process arguments use `ArgumentList`, never a shell command. Task metadata is atomically replaced on disk. Interrupted tasks become `interrupted` on restart and are not blindly rerun; repositories and worktrees are preserved for recovery.

`GET /tasks/:id` exposes pending approval request IDs and bounded `pendingApprovals` details: actual method, command or observed file paths, requested context, `detailsAvailable` and `redacted`. Suspected credential content is withheld; missing, truncated or redacted details disable approval in the worker itself. Details are available only through the authenticated task endpoint and never enter general events or logs. `/approvals/:requestId` accepts `accept`, `decline` or `cancel` for command/file-change requests. Unsupported server requests get a JSON-RPC method error, never an automatic approval. `/input` steers the current turn with its exact expected turn ID. `/cancel` interrupts and terminates the process tree; preparation commands also receive cancellation. `/drain` rejects new dispatches while existing work continues. `/events` replays at most 256 normalized state-only records with sequence IDs. It deliberately excludes raw model/tool output, prompts and authentication data. [Task output readback](task-output.md) provides a separate bounded, sanitized transcript with replay cursors and explicit gaps. Non-command/file approval types remain unsupported.

## Verification and limits

Build and protocol-focused checks must run locally, outside hosted release workflows. `dotnet run --project worker/tests/Worker.Checks.csproj` passes thirty-five checks covering certificate positive/negative paths, bounded replay, restart recovery, URL rejection, actual native ConPTY child output/exit status, official pairing field/expiry parsing, public CSR generation, retry key preservation and the task-output protocol/privacy/replay checks documented in [task output](task-output.md). Service hosts can inherit redirected streams, so the terminal child explicitly reopens its attached console handles before starting the CLI. End-to-end native service installation, real account device authentication, SSM mTLS connection, pairing connection verification and an actual authenticated model turn require configured enrollment and account access. A successful compilation does not prove those operations. This revision restricts repository input to ordinary `github.com/owner/repository` HTTPS URLs and disables clone redirects. Production enrollment ACL verification and downstream DNS enforcement remain required before accepting an untrusted controller.
