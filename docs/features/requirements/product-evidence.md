# Real screenshots wherever a surface is described

Every README and GitHub Pages carries real screenshots of every surface that has one, the main screen, each destination, settings, editors, dialogs, empty and error states, the narrow layout, and both themes, grouped under collapsible headings with alt text naming what each shows. They come from the real built artifact through the project's own harness at a known commit, never from mockups, and documentation articles and interface-changing release notes follow the same rule. Visual tasks retain inspected, provenance-bound screenshots in the repository's evidence folder, and a surface that cannot be captured yet says so where the image would go; after a UI remake or interface-changing delivery, refresh every current presentation screenshot and reference across application, GitHub Pages, README, documentation, wiki, gallery and download surfaces from inspected genuine source/hash-bound rebuilt states/configurations, preserving historical originals and provenance without false current claims. Every repository README carries source-controlled workflow diagrams with labelled rectangular steps, arrows and branches, preferring Mermaid top-to-bottom flow for narrow reading; missing diagrams are inventoried and backfilled on touched repositories, and extra views clarify architecture, data movement or lifecycle, and optional generated illustrations never replace workflow semantics. planning mode includes a diagram when it materially clarifies the plan, while every GitHub Pages supplies accessible animated diagrams with selectable workflow steps, access modes, or relevant configuration, pause and replay, reduced-motion support, and clearly labelled illustrative behavior; static README images link to that active equivalent and never substitute for real screenshots.

## Applicability

Applicable product surfaces must implement this behavior individually. A feature on one surface does not establish delivery on another.
